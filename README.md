# PinForge — Wokwi-style STM32 (Blue Pill) simulator with an in-browser C workflow

Web app + small compile server. You write C in the browser, the server builds it with `arm-none-eabi-gcc`,
and the page runs the result on an emulated Cortex-M3 / STM32F103 wired to a virtual circuit.

```
src/                source of the page (edit here, then `node tools/build.js`)
  core/             Cortex-M CPU, exceptions, NVIC, SysTick, bus router - knows no chip
  chip/             one file per chip: memory map, clock tree / system control, IRQ numbers, wires peripherals to the core (stm32f103.js, lpc1768.js)
  peripheral/       reusable on-chip peripherals: F1 (gpio-f1, exti-f1, usart-v1, adc-f1, timer-gp16, i2c-v1) and LPC17xx (gpio-lpc17 incl. pin connect + GPIO/EINT interrupts, timer-lpc17, uart-lpc17)
  ui/               editor, circuit canvas, wiring, inspector, docks, firmware loader
  parts/            external parts: LCD, 7-segment, keypad, servo..., I2C bus model and I2C sensors
  manifest.json     build order;  index.template.html = markup + CSS
public/index.html   GENERATED by tools/build.js (one self-contained file; commit it, it is what gets deployed)
server.js           zero-dependency Node server: static files + POST /api/compile + GET /api/health
toolchain/          startup code, linker script and the stm32f1.h register header used for every build
examples-src/       C sources + circuits of the shipped examples (tools/build-examples.js compiles them into src/ui/examples-data.js)
toolchain/lpc17xx*   LPC1768 header, startup, linker script and the boot-ROM checksum tool (lpc-checksum.js); the compile server takes {target:'lpc1768'}
tests/hw-validation/ one firmware + compare tool to check the simulated LPC1768 against a real board (see its README)
tests/              headless test suite (see Tests);  tests/ref/ holds the frozen v1 emulator used as an oracle
Dockerfile          node:20-slim + gcc-arm-none-eabi
render.yaml         one-click blueprint for Render (free plan)
```

## Architecture (emulator)
A chip is a `CortexM` core plus attached peripheral modules:
```js
const T = new CortexM(host, {flashBase, flashSize, flashAlias, ramBase, ramSize, ramBanks, cpuid});
T.attach({ name, regions:[[lo,hi]], rd(a,n), wr(a,n,v), reset(), post(), tick(cycles), level() });
```
`level()` raises level-sensitive IRQs with `T.irq(n)`; the chip file supplies base addresses, IRQ numbers, clock gates and pin maps to each module.
`chip/stm32f103.js` and `chip/lpc1768.js` exist today; a new chip is a new file in `chip/` (plus new peripheral modules where the silicon differs, e.g. an F4 GPIO with MODER).
After editing `src/` run `node tools/build.js`; `tests/run-all.sh` refuses to run if `public/index.html` is stale.
`tests/t_equiv.js` runs the frozen pre-refactor emulator and the current one in lockstep on every test firmware and shipped example and compares CPU state, interrupts and every host callback.

See `LPC1768_STATUS.md` for what the LPC1768 model covers and what is still open.

## Boards
The page has a board selector (top bar). A board is one object in `src/ui/board-*.js` (see the header comment of `src/ui/boards.js`): pins and their wire directions, the artwork (dynamic SVG and / or a static background layer), the chip constructor, flash map, UART pin, build target, parts it can drive. Examples carry a `board` field and are listed only for their board.
* `bluepill`: STM32 Blue Pill (STM32F103C8T6).
* `lpc1768`: PinForge LPC1768 board (two 2x19 headers, artwork generated by `python3 tools/gen_lpc_board.py`). The ADC is simulated (potentiometer works); parts that need I2C or PWM outputs (servo, I2C devices) are not offered on it until those peripherals exist.
Adding a board: write `src/ui/board-<name>.js`, add it to `src/manifest.json`, give its examples `"board": "<id>"` in `examples-src/examples.json`, run `node tools/build-examples.js` and `node tools/build.js`.

## Run locally
```
docker build -t pinforge . && docker run -p 3000:3000 pinforge     # then open http://localhost:3000
# or, without Docker: install arm-none-eabi-gcc, then
node server.js
```

## Deploy for free (Render)
1. Create a GitHub repository and push this folder to it.
2. On render.com: **New → Blueprint** (uses `render.yaml`) or **New → Web Service → Docker**, choose the **Free** plan.
3. Wait for the build. Your URL looks like `https://pinforge-xxxx.onrender.com`.

Free-tier notes (check current terms; they change): Render's free web service has 512 MB RAM and a small CPU share,
sleeps after about 15 minutes without traffic and takes roughly a minute to wake. Hugging Face Docker Spaces and
Fly.io no longer have a free option as of the sources checked in late 2026. If you only need the simulator
without the compile button, `public/index.html` also works on any static host (GitHub Pages, Netlify, Cloudflare Pages);
users then load firmware files built on their own machine.

## Using it
* **Layout:** Code / Circuit / Split tabs at the top; a dock with **Serial Monitor**, **CPU Registers**, **Logic Analyzer**, **I²C Monitor** and **Build Log** tabs at the bottom. The round **+** button inside the circuit area adds parts.
* **Build and Run are separate.** Build (Ctrl+B) compiles `main.c` only. Run (Ctrl+Enter) starts the last successful build and refuses a stale one. Prebuilt examples run immediately.
* **The circuit is locked while running:** no wiring, moving, adding, deleting or rotating, and `diagram.json` becomes read-only. Pressing buttons and turning potentiometers still works. Press Stop to edit again.
* **Wires** are right-angle lines on a 20 px grid (select a wire and drag its square handle to move the bend). Every pin sits on the grid.
* Without a compile server the editor is read-only; use **Load…** with a `.bin`, `.elf` or `.hex`.
* Build flags: `-mcpu=cortex-m3 -mthumb -Os -Wall -Wextra -nostdlib -ffreestanding`, linked with `toolchain/startup.c` and `link.ld` (64 KB Flash at 0x08000000, 20 KB RAM at 0x20000000).
* Allowed includes: `<stdint.h>`, `<stdbool.h>`, `<stddef.h>`, `"stm32f1.h"`, `"stm32f10x.h"` (alias, so ST-style code builds unchanged).

## Input / output devices
Add them with the **+** button. Each one is tested against real compiled firmware, and the examples come with the wiring already done (pick one from the project list).
* **LCD 16x2 (HD44780):** 4-bit and 8-bit interface, clear/home/entry mode, cursor and blink, display shift, DDRAM address wrap, 8 custom characters, display on/off. Wire VSS to GND, VDD to 5V, RW to GND, plus RS, E and D4-D7 (or D0-D7); A/K are the backlight (unwired = on). Write-only: it ignores read cycles, so keep RW low and use delays instead of the busy flag. Characters: ASCII, degree sign, arrows and a solid block.
* **7-segment digit** and **4-digit 7-segment (multiplexed):** common cathode or anode (inspector), decimal point, any colour. Multiplexed displays are time-averaged, so brightness follows the duty cycle and slow scanning flickers like the real thing.
* **Keypad 4x4:** a real row/column matrix. Click keys (works while running) or type 0-9 * # A-D on the keyboard. A short tap is held for 45 ms so firmware polling can see it.
* **Buzzer:** the tone frequency is measured from the pin edges (PWM or GPIO) and played through the browser speaker; mute it in the inspector.
* **RGB LED:** common cathode or anode, PWM duty is averaged per colour.
* **Slide switch**, **LED bar graph (10 LEDs)** and **Servo:** the angle comes from the measured pulse width (default 1.0-2.0 ms = 0-180 degrees, adjustable) and the servo needs V+ and GND wired.
* **OLED 128x64 (SSD1306, I2C):** the common 0.96" module, drawn with its 4-pin header on the top edge. Wire GND, VCC (3V3 or 5V), SCL and SDA to a real I2C pin pair: **I2C1 = PB6/PB7** (PB8/PB9 after `AFIO->MAPR |= AFIO_MAPR_I2C1_REMAP`) or **I2C2 = PB10/PB11**; the pins must be configured as alternate-function open-drain (`GPIO_AF_OD_50MHZ`). Inspector: colour (white, blue, yellow, or the yellow-top/blue-below two-colour glass), 128x64 or 128x32, I2C address 0x3C / 0x3D. Modelled like the chip: control bytes (Co / D/C#), page, horizontal and vertical addressing with column/page windows, contrast, invert, entire-display-on, display on/off, segment remap and COM scan direction (`0xA1`+`0xC8`, what Adafruit and u8g2 send, is upright, as on real glass), start line, multiplex ratio, charge pump (the screen stays dark until `0x8D 0x14` is sent, like the real module), horizontal scroll. Not modelled: vertical scroll offset, the SH1106 variant, reads. The glass shows a short hint while it is unpowered, waiting for data, or switched off.
* Wiring and editing are locked while running, but keypad keys, slide switches, pushbuttons and potentiometers stay usable.

## Logic analyzer
* **Auto mode:** with no Logic Analyzer part in the circuit, every active pin (outputs, pulled-up inputs, wired pins) gets a channel.
* **Probe mode:** add the **Logic Analyzer** part with the `+` button and wire D0-D7 to any pin or net (a button, an LED, a potentiometer, GND, 3V3...). Then exactly those channels are shown, named after what they touch.
* **Waveforms are cycle-accurate** for GPIO edges (1 kHz toggling measured at 1.000 ms), true timer **PWM** (period and duty measured to 0.1 %), and **UART TX** frames at the programmed baud rate (decoded back to the right byte). Analog nets (potentiometer) are drawn as analog traces with a voltage readout. Undriven nets are drawn dashed.
* Windows from 1 ms to 10 s, a **Hold** checkbox to freeze the view, a hover cursor with time readout, and frequency / duty cycle shown for periodic signals.
* **I2C:** SCL and SDA are recorded as real waveforms (SCL period from the programmed CCR, START / STOP / repeated START, 9 clocks per byte, data changes after SCL falls) and named `PB10 · I2C2 SCL` etc. The **I²C Monitor** tab decodes the same traffic: time, bus, S / Sr, address, R/W, ACK/NACK, bytes (a `!` marks a NACKed byte) and P. History is the last ~90 000 edges per channel (about 0.3 s of 100 kHz traffic).
* Limits: no trigger, no SPI decoding (SPI is not modelled yet), and signals changing faster than one pixel per window merge visually - zoom in with a shorter window.

## Security notes (read before exposing publicly)
Compiling strangers' C code is risky. Protections in `server.js`: source size cap; the code is preprocessed first and the
files actually included are checked (only the toolchain headers are allowed); inline assembly is limited to a few
instructions (wfi, wfe, nop, sev, cpsid/cpsie i, dmb, dsb, isb, bkpt); `#pragma`, `##` and `.incbin`-style tricks are rejected;
the compiler runs with CPU/memory/file-size limits (`prlimit`), a timeout, in a throw-away temp directory, as a non-root user;
builds are rate-limited per IP and at most two run at once. This is defence in depth, not a full sandbox — keep secrets
out of the container and let the platform's container isolation be the final barrier.

## Emulator coverage
Cortex-M3 (Thumb/Thumb-2 incl. IT blocks, UDIV/SDIV, 64-bit multiply, LDRD/STRD, TBB/TBH, bitfields), GPIO A/B/C,
RCC clocks (HSI, HSE, PLL -> up to 72 MHz), TIM2-4 (update + compare interrupts, PWM), USART1-3 (TX/RX), ADC1 (software-triggered).

**Interrupts:** NVIC enable/disable/set-pending/clear-pending, 4-bit priorities with preemption (a more urgent interrupt
interrupts a running ISR; equal priority waits), tail-chaining, PRIMASK (`__disable_irq`), SysTick, SVC, PendSV,
EXTI0-15 with AFIO line selection (rising/falling edge, software trigger), TIM2-4 update and compare interrupts,
USART1-3 RXNE/TXE/TC interrupts, ADC end-of-conversion. Sources are level-sensitive like the real chip: forgetting to clear a
flag (EXTI->PR, TIMx->SR, ...) makes the ISR re-enter endlessly. Exception entry/return costs 12 cycles each.
Header helpers: `NVIC_EnableIRQ/DisableIRQ/SetPriority/SetPendingIRQ/ClearPendingIRQ`, `__disable_irq`, `__enable_irq`, `__WFI`, `__SVC0`.

**I2C1 / I2C2 (master), built to behave like the silicon:**
* Registers `CR1/CR2/OAR/DR/SR1/SR2/CCR/TRISE` per RM0008: START, repeated START, STOP, 7-bit addressing, master transmitter (TXE / BTF, DR double buffering), master receiver with the three official sequences (N=1, N=2 with POS, N>2), ACK/NACK control, `ADDR` cleared only by an SR1 then SR2 read, `AF` on a NACK (write-0-to-clear), `ARLO`, `SWRST`, `PE=0`, reset through `RCC->APB1RSTR`, event and error interrupts (`I2Cx_EV_IRQn`, `I2Cx_ER_IRQn`, level-sensitive).
* **Clocking is checked like the chip does it.** `CR2.FREQ` must be 2..50 (MHz) and PCLK1 must be at least 2 MHz (standard mode), 4 MHz (fast mode) or 10 MHz (fast mode with DUTY=1); otherwise START never completes. SCL period is `2 x CCR` (standard) or `3 x CCR` / `25 x CCR` (fast, DUTY) PCLK1 cycles plus the real rise and fall time of the bus, so 100 kHz / 400 kHz code runs at the right speed and an out-of-spec divider gives an out-of-spec clock.
* **The bus has electrical rules** (see *I2C bus model* below). Without pull-up resistors a transfer cannot finish: no pull-up on SCL hangs the peripheral, no pull-up on SDA loses arbitration (`ARLO`) as soon as the address contains a 1; SCL or SDA shorted to GND (or driven low by another pin) makes `BUSY` read 1 and START wait; pins that are not alternate-function open-drain cannot drive the bus.
* The peripheral supports slave clock stretching (extra cycles after a byte), but no shipped part stretches yet.
* Not modelled: slave mode, 10-bit addressing, general call, SMBus/PEC, DMA requests, BERR and TIMEOUT flags, multi-master arbitration with another master.
`stm32f1.h` has the `I2C_TypeDef`, bit names (`I2C_CR1_START`, `I2C_SR1_TXE`, ...), `RCC_APB1ENR_I2C1EN`, IRQ numbers and `GPIO_AF_OD_*MHZ`.

**I2C bus model (what a real board would do):**
* **Pull-ups.** SCL and SDA each need a resistor to 3V3/5V. Modules that carry them (OLED, MPU-6050, BME/BMP280, BH1750, DS3231, DS1307, LCD backpack) pull up to *their own* supply (switchable in the inspector, "on-board pull-ups"); a bare AT24Cxx module has none, so wire two resistors (set `value`, e.g. 4700) between SCL/SDA and 3V3. Resistors in parallel combine.
* **Rise time and drive strength.** `t_r = 0.8473 x R x C` with C = 15 pF + 10 pF per device. More than 1.5x the limit (1000 ns at 100 kHz, 300 ns at 400 kHz) garbles transfers (NACK); pull-ups below about 1 kohm (3 mA sink limit) garble them too. Marginal values are reported.
* **Supply and levels.** A module needs its VCC in range (3.3 V-only modules such as the BMP280/BME280 breakouts are *destroyed for the run* on 5 V, or when the bus is pulled up to 5 V), a GND connection, and the bus must reach 0.7 x VDD to be seen (a 5 V LCD backpack on a bus pulled to only 3.3 V does not answer). The DS1307 needs 4.5 V.
* **Speed limits.** Parts that cannot run at the programmed SCL frequency do not answer: DS1307 and PCF8574 backpack 100 kHz, others 400 kHz (BMP/BME280 3.4 MHz).
* **Addresses.** Chosen by the real pins (AD0, SDO, ADDR, A0-A2) or jumpers (attributes); two devices with the same address both answer (writes reach both, reads are wired-AND) and the clash is reported.
* **Diagnostics.** Every one of these conditions is explained at the top of the **I²C Monitor** tab, with a timestamp, in plain words; the bus traffic below it is decoded.

**Parts on the I2C bus** (inspector values can be changed while the program runs; sensor readings are noise-free):
| Part | Address | Modelled behaviour |
|---|---|---|
| OLED 128x64 / 128x32 (SSD1306) | 0x3C / 0x3D | command and GDDRAM model, charge pump, addressing modes, scroll |
| MPU-6050 (GY-521) | 0x68, 0x69 with AD0 high | starts asleep (`PWR_MGMT_1 = 0x40`), 20 ms accel / 35 ms gyro start-up, full-scale ranges, temperature, device reset, `INT` data-ready (pulse stretched to 200 us, or latched until `INT_STATUS` is read). Not modelled: FIFO, DLPF filtering, auxiliary master, motion interrupts |
| BMP280 / BME280 | 0x76, 0x77 with SDO high (CSB low = SPI = no I2C) | calibration registers, `ctrl_meas`/`ctrl_hum`/`config`, forced and normal mode, measurement time, standby time, IIR filter, oversampling resolution, `status`. Raw values are generated so that Bosch's own compensation formulas return exactly what you set |
| DS3231 module (RTC + AT24C32) | 0x68 and 0x57 | time/date registers stored per field, running in simulated real time, weekday counter, 12/24 h, alarms 1 and 2 with flags, `INT/SQW` output (alarm or square wave up to ~2 kHz), temperature registers; the on-board EEPROM has ACK polling and page wrap. Not modelled: 32 kHz output, aging offset effect |
| DS1307 | 0x68 | halted clock without battery (`CH=1`), 56 bytes RAM, `SQW/OUT`, 100 kHz limit, needs 4.5 V |
| BH1750 (GY-302) | 0x23, 0x5C with ADDR high | power/measurement commands, 120 ms / 16 ms measurement time, 1.2 counts per lux, measurement-time register. It accepts a measurement command even before "power on" (real silicon is believed to do the same; not confirmed in the datasheet) |

Not modelled yet: BASEPRI and priority sub-grouping (PRIGROUP), USART error flags/idle line, DMA, SPI, watchdogs, ST's HAL / CubeMX projects, RTC,
flash/power control registers (so ST's HAL start-up code may hang), timer input capture, USB, CAN. `WFI` behaves like `NOP`.

## Tests
`tests/` compiles real firmware with `arm-none-eabi-gcc` and runs it against the emulator and the real page (jsdom, headless). Needs `arm-none-eabi-gcc` and `npm i --no-save jsdom`.
```
sh tests/run-all.sh      # or: npm test
```
* `t_core1/2/3`: the I2C peripheral against a mock bus (writes, NACK, 1/2/5-byte reads, interrupts, fast mode, `PE`/`SWRST`, invalid FREQ/PCLK1, arbitration loss, hangs, bus held low, rise time, clock stretching).
* `t_ssd`: the SSD1306 model. `t_isa`: executes every distinct instruction in every compiled binary once, so an instruction the emulator lacks is found here and not in your program.
* `e2e_i2c`, `e2e_more`: the page end to end (OLED pixels read back, SCL/SDA waveforms decoded independently and compared with the monitor, scanner, I2C1 remap, probes, diagram.json).
* `e2e_sensors`: every sensor with firmware that reads it, checked against the datasheet math (Bosch's integer compensation for BMP/BME280, MPU-6050 scaling, RTC rollover and alarms, EEPROM page wrap...).
* `e2e_rules`: the electrical rules (missing/strong/weak pull-ups, shorts, over-voltage, logic levels, speed limits, duplicate addresses).
* `e2e_examples`: the shipped sensor examples as a user runs them, including a Stop/Run cycle.

## LPC1768 status
Implemented: Cortex-M3 core with 5 priority bits, 512 KB flash at 0 + 32 KB local SRAM + two 16 KB AHB SRAM banks, boot-ROM checksum, system control (IRC / main oscillator, PLL0 with feed sequence and lock time, CCLKCFG, FLASHCFG, PCONP, PCLKSEL0/1), pin connect (PINSEL / PINMODE / open drain), fast GPIO with FIOMASK, GPIO interrupts (ports 0 and 2), EINT0-3, Timer0-3 (match / reset / stop, prescaler), UART0-3 (fractional baud, FIFOs, THRE / RDA / timeout / overrun interrupts).
The model reports (through `host.diag`) the mistakes real silicon makes you pay for: FLASHTIM too short for CCLK, PLL0 out of range, unpowered peripherals, UART pins not selected.
Not yet: ADC, I2C0-2, SSP/SPI, PWM1, RTC, DAC, DMA, capture inputs / match outputs on timers, UI board for the LPC1768.
